## Description

[Nest](https://github.com/nestjs/nest) framework TypeScript starter repository.

## Project setup

```bash
$ npm install
```

## Compile and run the project

```bash
# development
$ npm run start

# watch mode
$ npm run start:dev

# production mode
$ npm run start:prod
```

## Run tests

```bash
# unit tests
$ npm run test

# e2e tests
$ npm run test:e2e

# test coverage
$ npm run test:cov
```

```bash

```

With Mau, you can deploy your application in just a few clicks, allowing you to focus on building features rather than managing infrastructure.

## Preguntas de Cierre

1. ¿Por qué OrderPriorityService no necesita un repository?

OrderEntity es recibido y ya está cargado con status y quantity. No requiere un repository debido a que no es necesario consultar en la base de datos. OrderService es quien trae el pedido de la base de datos.


2. ¿Qué responsabilidad tiene OrdersService al consultar la prioridad?

OrdersService realiza la busqueda del pedido en la base de datos. identifica la prioridad en orderPriorityService. Hace la conexión entre el repository (datos) y el servicio de dominio (reglas).


3. ¿Cuál es la diferencia entre totalPending y showing?

TotalPending indica el número total de pedidos con el estatus 'pending'. Showing es orders.length, cuántos pedidos se están retornando.


4. ¿Por qué las pruebas de prioridad pueden ejecutarse sin PostgreSQL?

El servicio no tiene dependencias externas, se crea el objeto con new OrderPriorityService() y los pedidos se arman con buildOrder(...). No hay conexión a base de datos.


5. ¿Qué problema de diseño aparecería si la prioridad se calculara en el controller?

Si la prioridad se formara en el controller, se mezclarían las capas de HTTP y lógica de negocio: el código resultaría más complejo de testear, no se podría aplicar esta lógica desde otro dispositivo, y no seguiría el patrón (Controller → Service → Repository).
